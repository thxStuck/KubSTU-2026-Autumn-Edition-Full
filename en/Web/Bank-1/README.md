# Bank-1

> **Category:** Web · **Event:** KubSTU CTF 2026 Autumn

## 📌 Task

CAPY-CAPY is a Flask-based internet bank. The flag is sold in a closed "Flag Shop" available only to premium customers; the payment is debited from the account and confirmed by a Telegram bot via a one-time offer token.

The only premium user is `mgalankov@4274`, with account `ACC004` and a balance of about 1.49 million ₽. The flag costs 1000 ₽, so the whole task boils down to one thing: make a payment on his behalf.

![The bank's landing page](../../../assets/Web/Bank-1/01_landing.png)

*The starting point. Nothing but a login and registration form — the storefront gives away neither usernames nor account numbers.*

Every transfer is signed with a 16-character HMAC signature that the server issues **only** after verifying a PIN code. The PIN is eight digits, it is not stored in plaintext, and brute force is limited to 20 attempts per minute. This is exactly the wall the challenge asks you to get around.

## 🏁 Solution

### Summary

A chain of three independent flaws. None of them alone yields the flag; together they give a full takeover of someone else's account.

| # | Vulnerability | Essence |
|---|---|---|
| 1 | Broken access control (CWE-639) | The internal password-reset endpoint does not check the role and returns the victim's login in the response |
| 2 | Second-factor leak (CWE-200) | The OTP request returns the code itself right in the HTTP response body |
| 3 | Mixing of secret namespaces | The 2FA code and the payment signature are produced by the same generator, so the OTP is accepted in place of the signature |

### Stage 0. Reconnaissance

We register an ordinary account — it is needed as a foothold: almost all of the interesting endpoints require a valid JWT.

![Registration form](../../../assets/Web/Bank-1/02_register.png)

*The form requires a Russian full name, a driver's license and an ALTCHA PoW captcha. The login is generated by the server: the first letter of the first name + transliterated surname + four random digits.*

Next comes the key observation of the whole recon. In the site footer there is an "API Documentation" link, and it leads to an **open Swagger with no authorization**.

![Swagger UI](../../../assets/Web/Bank-1/04_swagger_top.png)

*`/api/docs` — the full specification is served anonymously. It lists endpoints that the interface has no link to anywhere.*

![Administration section](../../../assets/Web/Bank-1/05_swagger_admin.png)

*The "Administration" section — a single endpoint: `POST /api/admin/reset_password`, "sets a new password for a user by their identifier".*

> **Why this is a find.** The interface does have a password change — on the "Profile" page. But that form requires the current password and changes only your own. The endpoint from Swagger requires neither, and it accepts *someone else's* identifier.

### Stage 1. IDOR: someone else's password and a login leak

The endpoint is protected only by `@jwt_required()` — i.e. it checks that the caller is logged in at all, and nothing more:

```python
# app.py — /api/admin/reset_password
target = User.query.get(target_user_id)
# нет проверки роли и нет сверки target_user_id с текущим пользователем
target.password = generate_password_hash(new_password)
```

The identifiers are small integers, so we enumerate them one by one. And here is the second flaw: **the response returns the login** of the user whose password we have just changed. Knowing the victim's nickname in advance is not required — the endpoint names it itself.

![Enumerating target_user_id](../../../assets/Web/Bank-1/06_idor_enum.png)

```
uid=1 [200] Пароль пользователя aalice@1234 изменён
uid=2 [200] Пароль пользователя bbob@5678 изменён
uid=3 [200] Пароль пользователя ccharlie@9012 изменён
uid=4 [200] Пароль пользователя mgalankov@4274 изменён   ← премиум
uid=5 [200] Пароль пользователя ihakerov@1424 изменён    ← это мы сами
uid=6 [404] Целевой пользователь не найден
```

Which of the four is premium is not known in advance, but there are only four: we log in one after another and see whose shop opens.

We log in as `mgalankov@4274` with the password we assigned ourselves.

*Account ACC004, balance 1,486,808.50 ₽ and a payment history. The account is ours.*

![Flag Shop](../../../assets/Web/Bank-1/08_flag_shop.png)

*The "Flag Shop" opened — the `user.is_premium` check passed.*

### Stage 3. The wall: the PIN code

We enter the offer token, click "Buy" — and run straight into the thing the challenge exists for.

![PIN code prompt](../../../assets/Web/Bank-1/09_pin_wall.png)

*To obtain the transaction signature you need an eight-digit PIN. Brute-forcing 10⁸ options at a limit of 20 requests per minute would take millennia.*

The intended flow: the page sends the PIN to `/api/get_signature`, the server verifies it and issues a signature hard-bound to the recipient, the amount and the description. The signature is one-time and lives for five minutes. It cannot be forged — the HMAC key is on the server.

So the signature must not be forged but *obtained legitimately through another channel*.

### Stage 4. The second factor that gives itself away

In Swagger there is a "Security" section with the endpoint `POST /api/2fa/send` — "sends an OTP to confirm a transfer". We call it and look at the response:

![OTP leak](../../../assets/Web/Bank-1/10_otp_leak.png)

```json
POST /api/2fa/send  {"purpose": "transfer"}

{
  "masked_number": "+7-***-**-****",
  "otp": "31f0818ebf466718",
  "status": "sent",
  "timestamp": 1789858049
}
```

The phone number is carefully masked — but the one-time code itself lies in the response in plaintext.

> **The detail that decides everything.** The OTP is not six digits from an SMS. It is *16 hexadecimal characters* — exactly the format in which the bank prints the transaction signature on the receipt.

### Stage 5. OTP instead of the signature

The format matches not by accident. The 2FA code is produced by the same generator as the payment signature:

```python
# app.py — генерация 2FA-кода
ts  = int(datetime.now(timezone.utc).timestamp())
otp = generate_signature_from_timestamp(ts)   # тот же HMAC, что у подписи
```

And the transfer handler, failing to find the signature in the list issued for a PIN, goes looking for it among the unused OTPs — and accepts it:

```python
# app.py — /transfer
ok, reason = consume_pending_signature(...)   # не прошло: PIN мы не вводили
if not ok:
    otp_rec = TwoFactorCode.query.filter_by(
        user_id=user.id, code=transaction_signature,
        purpose='transfer', used=False).first()
    if otp_rec:
        ok = True
        transaction_timestamp = otp_rec.signature_timestamp
```

We submit the transfer form manually, putting the OTP into the `transaction_signature` field. We do not enter a PIN at all:

```http
POST /transfer

to_account             = FLAG_SHOP
amount                 = 1000.00
product_id             = 1
token                  = <offer-токен из Telegram-бота>
transaction_timestamp  = 1789858049
transaction_signature  = 31f0818ebf466718   ← это OTP
```

![Purchase confirmed](../../../assets/Web/Bank-1/11_purchase_ok.png)

*"Purchase confirmed! The flag has been sent to the Telegram bot." The balance decreased by exactly 1000 ₽.*

The receipt leaves no doubt that it was precisely the one-time code that served as the signature:

![Transaction receipt](../../../assets/Web/Bank-1/12_receipt.png)

*The "Transaction signature" field — `31f0818ebf466718`, the same OTP.*

### Flag

```
KubSTU{0tp_1s_th3_s1gnatur3_c4py_b4nk_0wn3d}
```

The bot stores only the inner part in `FLAG_CONTENT` and wraps it itself (`f'KubSTU{{{flag_content}}}'`). After a confirmed purchase it sends the string as a message and duplicates it as a `flag.txt` file.

### Root cause: what's wrong with the signature

The signature is computed from only two fields:

```python
# notquiterandom.py
message = timestamp.to_bytes(8, "big") + counter.to_bytes(8, "big")
mac = hmac.new(self._key, message, hashlib.sha256).digest()
```

It contains neither the amount, nor the recipient, nor the sender. The only thing that tied the signature to a specific payment was the server-side whitelist, into which an entry got after a PIN check. The OTP branch bypasses this whitelist entirely, and with it the whole binding falls away: a single issued OTP authorizes a transfer **to any account and for any amount**.

Cryptography has nothing to do with it here — HMAC-SHA256 is honest and the key did not leak. What is broken is the trust model: a secret issued for one purpose (to confirm that the user has a phone) is accepted for another (to confirm that the user authorized a specific payment).

### What gets in the way

| Mechanism | What it does | How it is bypassed |
|---|---|---|
| ALTCHA PoW captcha | Required on login, registration, password reset and the OTP request. The challenge is one-time and lives 120 s | Solved in the browser: find `n` such that `sha256(salt + n)` equals the challenge |
| Anti-bot by User-Agent | Cuts off `python-requests`, `curl`, `HeadlessChrome` and the like on POST requests | Work from a real browser or set an ordinary UA |
| Rate limit | Password reset — 10/min, PIN check — 20/min, per IP | Enumerating five IDs fits within the limit; it will never be enough to brute-force the PIN |

> **A dead end worth mentioning.** On the "Security" page there is a two-factor toggle. It writes the `is_2fa` field, which is never read in the transfer logic — toggling it changes nothing. A false trail.

### How to fix

1. **Add a role check** to `/api/admin/reset_password` and do not return the login in the response — a neutral "done" is enough.
2. **Never hand out the OTP in the HTTP response.** The second factor must travel over a different channel, otherwise it is not a second one.
3. **Separate the secret namespaces.** The OTP and the payment signature must be computed with different keys and with a different context — then substituting one for the other stops working in principle.
4. **Sign the payment itself.** Include the sender, recipient, amount and description in the signature, not just the timestamp.
5. **Remove the bypass branch** in `/transfer`: the signature is accepted only from the whitelist issued after a PIN.
6. **Differentiate the login responses.** Right now "user not found" and "wrong password" are different messages, which by itself allows enumerating logins.
